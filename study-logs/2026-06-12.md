## 1. 역할 기반 접근 제어 (Role-Based Access Control)

### `getAuthorities()` 구현

`UserEntity`가 `UserDetails`를 구현하면서 `getAuthorities()`를 실제로 채워야 했다.
ADMIN은 ADMIN + USER 권한을 모두 가지도록 설계했고, `ROLE_` 접두사가 붙은 버전과 없는 버전을 함께 등록했다.

- `hasRole()` → 내부적으로 `ROLE_` 접두사를 자동으로 붙여서 비교
- `hasAuthority()` → 접두사 없이 정확히 일치하는 값을 비교

둘 다 처리하기 위해 두 형태를 모두 `SimpleGrantedAuthority`로 등록.

```java
// ADMIN인 경우
return List.of(
    new SimpleGrantedAuthority("ROLE_" + Role.ADMIN.name()),
    new SimpleGrantedAuthority(Role.ADMIN.name()),
    new SimpleGrantedAuthority("ROLE_" + Role.USER.name()),
    new SimpleGrantedAuthority(Role.USER.name())
);
```

### `SecurityConfiguration`에서 URL별 권한 설정

GET은 누구나 접근 가능하게 하고, 나머지(POST/PATCH/DELETE)는 ADMIN만 가능하도록 설정.
메서드별로 `requestMatchers`를 나눠서 명시적으로 지정했다.

```java
.requestMatchers(HttpMethod.GET, "/api/*/session-speakers", "/api/*/session-speakers/**")
.permitAll()
.requestMatchers("/api/*/session-speakers", "/api/*/session-speakers/**")
.hasAuthority(Role.ADMIN.name())
```

> `HttpMethod` 없이 패턴만 지정하면 GET을 제외한 모든 메서드에 매칭된다.
> Spring Security는 위에서 아래로 순서대로 매칭하므로 GET permitAll을 먼저 선언해야 한다.

## 2. 테스트 데이터 자동 생성 — DataFaker + ApplicationRunner

### DataFaker

랜덤 테스트 데이터를 생성해주는 라이브러리. 이름, 주소, 직업 등 현실적인 가짜 데이터를 간단히 만들 수 있다.

```kotlin
// build.gradle.kts
implementation("net.datafaker:datafaker:2.4.2")
```

```java
Faker faker = new Faker();
faker.name().fullName();  // "John Doe"
faker.internet().emailAddress();
```

### ApplicationRunner

스프링 부트 애플리케이션이 완전히 초기화된 후 실행되는 콜백 인터페이스.
서버 시작 시점에 초기 데이터 삽입, 캐시 워밍업 등 필요한 작업에 활용한다.

```java
@Configuration
public class ApplicationConfiguration {

    @Bean
    ApplicationRunner applicationRunner(...) {
        return args -> {
            // 앱 시작 후 자동 실행되는 로직
        };
    }
}
```

> `CommandLineRunner`와 비슷하지만 `ApplicationRunner`는 파싱된 `ApplicationArguments`를 받는다.

## 3. CrashSession 도메인 CRUD 구현

### 도메인 구조

SessionSpeaker와 동일한 레이어 구조로 구현했다.

```
model/crashsession/
├── CrashSession.java               # 도메인 DTO (Entity → DTO 변환용)
├── CrashSessionCategory.java       # Enum (카테고리 종류)
├── CrashSessionPostRequestBody.java
└── CrashSessionPatchRequestBody.java

model/entity/
└── CrashSessionEntity.java         # JPA 엔티티, SessionSpeakerEntity와 @ManyToOne 관계
```

### Partial Update 패턴

PATCH 요청에서 요청 바디의 각 필드가 비어 있지 않은 경우에만 업데이트하는 방식.
`ObjectUtils.isEmpty()`로 null 및 빈 값을 한 번에 체크했다.

```java
if (!ObjectUtils.isEmpty(requestBody.title())) {
    entity.setTitle(requestBody.title());
}
```

### 커스텀 예외

`CrashSessionNotFoundException`을 추가해 해당 sessionId가 없을 때 명확한 예외를 던지도록 했다.
기존 `SessionSpeakerNotFoundException`과 동일한 구조.

### Service에서 다른 Service 주입

`CrashSessionService`가 `SessionSpeakerService`를 `@Autowired`로 주입받아, 세션 생성 시 speakerId로 연사 엔티티를 조회해서 연결했다.

```java
var sessionSpeakerEntity =
    sessionSpeakerService.getSessionSpeakerEntityBySpeakerId(requestBody.speakerId());
```

## 4. DataFaker 상세 사용법

### `Faker` 인스턴스 재사용

`static` 필드로 선언해 매번 생성하지 않고 재사용했다.

```java
private static final Faker faker = new Faker();

faker.name().fullName();                       // 이름
faker.company().name();                        // 회사명
faker.shakespeare().romeoAndJulietQuote();     // 셰익스피어 로미오와 줄리엣 구절
faker.internet().emailAddress();              // 이메일
```

카테고리별로 다양한 도메인 데이터를 제공한다 (`name`, `company`, `internet`, `address`, `lorem` 등).

### `IntStream`으로 반복 생성

for문 대신 `IntStream.range()`로 n개의 테스트 데이터를 만들었다.

```java
private void createTestSessionSpeakers(int numberOfSpeakers) {
    IntStream.range(0, numberOfSpeakers)
        .mapToObj(i -> createTestSessionSpeaker())
        .toList();
}
```

## 5. 정적 팩토리 메서드 — setter vs. 필드 직접 할당

`Entity.of(...)` 형태의 정적 팩토리 메서드를 구현할 때 두 가지 방식이 있다.

### 방식 A — setter 사용 (이번에 선택한 방식)

```java
public static CrashSessionEntity of(String title, String body, ...) {
    var entity = new CrashSessionEntity();
    entity.setTitle(title);
    entity.setBody(body);
    // ...
    return entity;
}
```

- 기본 생성자(`new`) + setter 조합
- JPA가 기본 생성자를 요구하므로 어차피 `@NoArgsConstructor`(또는 `protected` 기본 생성자)가 있어야 한다
- setter가 이미 존재하는 경우 추가 코드 없이 재사용 가능

### 방식 B — 필드 직접 할당 / Builder

```java
// 필드 직접 할당 예시
entity.title = title;
entity.body = body;
```

또는 Lombok `@Builder`를 사용하면 팩토리 메서드 없이도 같은 효과를 낼 수 있다.

```java
CrashSessionEntity.builder()
    .title(title)
    .body(body)
    .build();
```

### 비교

| | setter 방식 | 필드 직접 할당 / Builder |
|---|---|---|
| setter 필요 여부 | 필요 | 불필요 |
| 불변성 | setter가 외부에 노출됨 | 외부 노출 없이 구성 가능 |
| JPA 호환성 | 기본 생성자 + setter 이미 있으면 자연스러움 | Builder + protected 생성자로 구성 가능 |
| 코드 양 | 간결 | Builder 설정 필요 |

> JPA 엔티티는 프록시 생성을 위해 기본 생성자가 필수다.
> 완전한 불변성은 어렵지만, setter를 `protected`로 제한하거나 Builder 패턴으로 외부 노출을 줄일 수 있다.
