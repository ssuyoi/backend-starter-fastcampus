# 2026-07-24 학습 로그

## GitHub 로그인 후 `999 No message available` 트러블슈팅

로컬에서 GitHub OAuth 로그인을 할 때마다 아래 JSON이 뜨는 문제를 추적한 기록.

```json
{"timestamp":"2026-07-23T16:00:31.515+00:00","status":999,"error":"None","message":"No message available"}
```

- 메인 화면으로 다시 이동하면 **로그인은 정상적으로 되어 있었음**
- 그런데 로그인할 때마다 반복
- 브라우저 쿠키를 지우니 사라짐

---

## 1. 결론 한 줄

**스프링 시큐리티가 세션에 저장해둔 "로그인 후 돌아갈 주소"가 `/error`였다.**

로그인이 실패한 게 아니라, 로그인은 성공했는데 **도착지가 이상했던** 것.

---

## 2. `999`가 의미하는 것

`DefaultErrorAttributes`가 응답을 만들 때의 로직:

```java
Integer status = getAttribute(requestAttributes, RequestDispatcher.ERROR_STATUS_CODE);
if (status == null) {
    errorAttributes.put("status", 999);
    errorAttributes.put("error", "None");
    return;
}
```

- `/error`는 원래 "몇 번 에러인지"를 request attribute로 **전달받아서** 화면에 표시함
- 그 값이 없으면 빈칸을 `999` / `"None"`으로 채움

> **999는 "에러가 났다"가 아니라 "에러 페이지가 에러 없이 열렸다"는 뜻.**
> 숫자가 커서 심각해 보이지만 오히려 반대다.

즉 `/error`에 **직접 접근(GET)** 했다는 신호. 진짜 500이 난 게 아니다.

---

## 3. forward vs 리다이렉트 — 이번 사건의 핵심

같은 `/error`인데 **어떻게 도착했느냐**에 따라 결과가 갈린다.

| | forward | 리다이렉트 |
|---|---|---|
| 주체 | 서버 내부 이동 | 브라우저가 새로 요청 |
| 주소창 | 안 바뀜 | 바뀜 |
| "404였다"는 정보 | **남아있음** | **사라짐** |
| `/error` 결과 | 정상 404 화면 | **999** |

- 404가 나서 `/error`로 가는 건 → **forward** (에러 정보 유지)
- 로그인 성공 후 `/error`로 가는 건 → **리다이렉트** (에러 정보 없음 → 999)

---

## 4. 전체 사고 흐름

```
크롬 DevTools가 자동 요청
/.well-known/appspecific/com.chrome.devtools.json
        ↓  앱에 없는 파일
      404 발생
        ↓  스프링이 에러 화면을 위해 forward
      /error 로 이동
        ↓  ERROR 디스패치에도 시큐리티 필터가 적용됨
"어? /error는 인증 필요한데?"  ← anyRequest().authenticated()
        ↓  ExceptionTranslationFilter
RequestCache(세션)에 "/error" 저장   ← 오염 지점
        ↓
      로그인 요구 → GitHub 인증 → 성공
        ↓  SavedRequestAwareAuthenticationSuccessHandler
저장된 "/error"로 리다이렉트
        ↓  에러 정보 없는 평범한 GET
      999 / "None"
```

### 왜 `/error`가 저장됐나

`SecurityConfig`에 이렇게 되어 있었다.

```java
.anyRequest().authenticated()   // 나머지는 전부 인증 필요
```

`/error`도 "나머지"에 포함된다. 스프링 입장에서는 `/error`가 그냥
**사용자가 가려던 페이지**로 보였고, 착실하게 세션에 메모해둔 것.

원래는 "로그인 전에 가려던 페이지로 돌려보내주는" 편의 기능인데,
엉뚱한 주소가 저장되면서 역효과가 났다.

---

## 5. 방아쇠: 크롬 DevTools

```
/.well-known/appspecific/com.chrome.devtools.json
```

- 내가 만든 요청이 아니라 **크롬이 DevTools를 열면 자동으로 찔러보는 주소**
- 워크스페이스 설정 파일이 있는지 확인하는 용도
- 앱에 없으니 404 → 위 연쇄의 시작점

DevTools를 켠 채로 로그인해보니 999 대신 아래 화면이 떠서 발견했다.

```
Whitelabel Error Page
There was an unexpected error (type=Not Found, status=404).
No static resource .well-known/appspecific/com.chrome.devtools.json.
org.springframework.web.servlet.resource.NoResourceFoundException
```

> 참고: 이 스택 트레이스는 `AuthorizationFilter`를 통과해서 `DispatcherServlet`까지
> 도달했다. 필터에서 막혔다면 거기까지 못 간다. → 이때는 **이미 로그인된 상태**여서
> 999가 아니라 정상 404가 나온 것.

**단, 방아쇠는 크롬 요청에 한정되지 않는다.**
인증 안 된 상태에서 404/500을 내는 요청이면 무엇이든 같은 구조로 문제를 만든다.
크롬 DevTools 요청은 그 대표적인 예시일 뿐.

---

## 6. 쿠키 삭제가 통한 이유

```
저장된 주소  →  세션 안에 있음  →  세션은 JSESSIONID 쿠키로 연결됨
```

쿠키를 지우면 새 세션이 생기고, 오염된 메모도 같이 사라진다.
**코드를 하나도 안 고쳤는데 해결된 이유**가 이것.

다만 증상만 없앤 것이라 조건이 갖춰지면 재발한다.

---

## 7. 대응 방향

### (1) 가장 간단 — `/error` 허용

`SecurityConfig`의 `permitAll` 목록에 `/error` 추가.
에러 페이지를 인증 뒤에 숨길 이유가 없으므로 타당하다.

### (2) 근본 대응 — RequestCache가 저장할 요청 제한

`/error`나 크롬 probe는 애초에 "사용자가 가려던 페이지"가 아니다.
그런 걸 저장하는 것 자체가 문제.

- `HttpSessionRequestCache#setRequestMatcher`로 저장 조건 지정
- `http.requestCache(...)`로 교체
- 흔히 쓰는 기준: **`Sec-Fetch-Dest: document`** 헤더
  (주소창 이동·링크 클릭에만 붙고, fetch/XHR/이미지 요청에는 안 붙음)

### (3) 아예 안 쓰기

이 앱은 `/`가 사실상 전체 화면이라 "원래 가려던 곳 복귀" 기능이 필요한지 의문.
필요 없다면 로그인 성공 후 목적지를 고정하는 쪽이 구조적으로 깔끔하다.

---

## 8. 배운 것

- **에러 코드를 액면 그대로 믿지 말 것.** 999는 에러가 아니라 "에러 정보의 부재"였다.
- **forward와 리다이렉트의 차이**가 실제 버그로 드러나는 사례를 처음 경험.
  둘 다 "다른 페이지로 간다"지만 request attribute의 생존 여부가 완전히 다르다.
- `anyRequest().authenticated()`의 "나머지"에는 **내가 만들지 않은 경로**도 포함된다.
  (`/error`, `/favicon.ico`, 브라우저의 자동 요청 등)
- 쿠키 삭제로 해결됐다는 사실 자체가 **"원인이 세션에 있다"는 강력한 단서**였다.
  증상이 사라졌다고 넘어갈 게 아니라 거기서부터 추적했어야 했다.

## 관련 삽질 메모 (별건)

`application.yaml`에서 발견한 오타 두 개.

```yaml
spl.init.mode: always                      # → sql.init.mode (data.sql이 실행 안 됨)
org.springframework.web.servelt: debug     # → servlet
```

- 앞의 것은 **스프링 설정 프로퍼티**라 이름이 틀리면 바인딩 실패 → 기본값으로 동작. 실제 영향 있음.
- 뒤의 것은 **로거 이름**이라 틀려도 무해. 게다가 위에 `root: debug`가 있어서 효과 자체가 없었음.
- 둘 다 오타지만 **성격이 다르다**는 점이 포인트. 999와는 무관.
