# 2026-07-21 학습 로그

## OAuth2 로그인 흐름 (GitHub)

강의를 따라 GitHub OAuth2 로그인을 구현하며, `SecurityConfig`와 `GithubUser` DTO가
어떻게 맞물려 동작하는지 흐름 중심으로 정리.

---

## 1. 전체 흐름

```
oauth2Login (withDefaults)
        ↓  스프링이 타입 매칭으로 커스텀 빈을 찾아 끼움
OAuth2UserService<OAuth2UserRequest, OAuth2User> 빈
        ↓  DefaultOAuth2UserService.loadUser(userRequest)
GitHub userinfo 엔드포인트 호출 → 원본 Map(attributes) 획득
        ↓  GithubUser.from(attributes)
우리 도메인 타입 GithubUser (OAuth2User 구현체)
```

핵심 한 줄:

```java
return userRequest -> GithubUser.from(delegate.loadUser(userRequest).getAttributes());
```

- `delegate.loadUser()` → GitHub에 실제 HTTP 요청, 프로필 응답 획득
- `.getAttributes()` → 응답을 `Map<String, Object>`(login, name, email, avatar_url ...)로 꺼냄
- `GithubUser.from()` → 그 Map을 우리 타입으로 변환

---

## 2. 커스텀 빈이 자동으로 주입되는 원리

`.oauth2Login(withDefaults())`만 있고 `.userInfoEndpoint(...)`로 명시 연결한 코드가 없어도 동작함.

- 스프링 시큐리티가 필터체인을 구성할 때 컨테이너에서
  **`OAuth2UserService<OAuth2UserRequest, OAuth2User>` 타입의 빈**이 있는지 찾음
- 있으면 기본값(`DefaultOAuth2UserService`) 대신 그 빈을 사용
- 특정 타입 빈만 등록하면 알아서 끼워주는 "커스터마이징 훅" 패턴

> 주의: 제네릭 타입을 하나라도 틀리게 쓰면 스프링이 못 찾고 조용히 기본 서비스를 써버림.

---

## 3. `getAttributes()`는 계약(contract)이다

`GithubUser`는 평범한 DTO가 아니라 **`OAuth2User`를 구현한 표준 타입**.
`OAuth2User`의 `getAttributes()`는 "provider 원본 속성을 돌려준다"가 계약 내용.

```java
// 잘못된 구현 — 계약 위반
@Override
public Map<String, Object> getAttributes() { return Map.of(); } // 빈 맵!
```

- `from()`에서 id/name/email 3개만 뽑고 원본 Map을 버리면,
  나중에 `user.getAttributes().get("avatar_url")` 같은 코드가 **조용히 깨짐**
- 겉으로는 "나 OAuth2User야" 하면서 핵심 메서드는 빈 맵 → 가장 나쁜 조합

### 올바른 방향 (원본 보관)

```java
public record GithubUser(Map<String, Object> attributes) implements OAuth2User {
    public static GithubUser from(Map<String, Object> attributes) {
        return new GithubUser(attributes);          // 원본 통째로 보관
    }
    @Override
    public Map<String, Object> getAttributes() { return attributes; } // 계약 준수

    public String id()    { return String.valueOf(attributes.get("login")); }  // 편의 접근자
    public String email() { return String.valueOf(attributes.get("email")); }
}
```

- id/name/email은 사라지는 게 아니라 **attributes 맵 안에** 다 들어있음
- "미리 뽑아 필드에 저장" → "맵에 두고 필요할 때 꺼냄"으로 바뀐 것뿐

---

## 4. `from()` vs `getAttributes()` — 방향이 반대인 짝

```
from()          : 원본 Map  ──변환──> GithubUser 객체   (입구, 생성)
getAttributes() : GithubUser 객체 ──꺼냄──> 원본 Map    (출구, 제공)
```

- 충돌하는 관계가 아니라 **입구-출구로 협력**하는 관계
- 입구(`from`)에서 원본을 잘 넣어둬야 출구(`getAttributes`)가 제대로 꺼내줄 수 있음

---

## 5. 왜 `implements OAuth2User`가 강제인가

`oAuth2UserService()` 빈의 반환 타입:

```java
OAuth2UserService<OAuth2UserRequest, OAuth2User>
```

두 번째 제네릭이 "이 서비스는 `OAuth2User`를 반환한다"는 계약.
→ `from()`이 돌려주는 `GithubUser`는 반드시 `OAuth2User`의 하위 타입이어야 컴파일 통과.

```
스프링 시큐리티가 OAuth2User 타입을 요구
        ↓
GithubUser는 OAuth2User를 implements 해야 함 (선택 아님)
        ↓
OAuth2User의 계약(getAttributes 등)을 지켜야 함
        ↓
따라서 원본 attributes를 버리면 안 됨
```

> "굳이 전체 데이터를 다 들고 있어야 하나?"에 대한 답:
> 일반 DTO였다면 필요한 것만 뽑는 게 옳다(YAGNI).
> 하지만 `OAuth2User`라는 표준 타입을 입는 순간, 계약 이행은 **의무**가 된다.
> Map은 로그인 시점에 이미 메모리에 있으므로 참조만 붙잡는 비용은 사실상 없음.

## 6. `getName()` 커스터마이징 이유

```java
@Override
public String getName() {
    return name.equals("null") ? id : name; // name 없으면 id로 폴백
}
```

- `getName()` 반환값 = 스프링 시큐리티가 사용하는 **principal 이름**(사용자 식별자)
- GitHub의 `name`은 **nullable**(프로필에 이름 안 넣은 사용자) → id로 폴백
- 이 nullable 특성 때문에 `from()`의 name/email에 `// nullable` 주석을 남김
